# 可行性研究报告

> 项目：SchoolLifeComplex 校园兴趣社区
> 编写：系统分析员2
> 版本：初稿
> 结论提要：**技术上完全可行，经济上无资金障碍，法律上存在必须回避的红线；真正的约束在组织侧。项目在"收敛范围 + 双通道准入"的前提下可行；若坚持"组织入驻为唯一入口"或"集成学校官方数据"，则不可行。**

---

## 一、可行性研究的对象与前提

本报告研究的问题是：**在三个人到四个人的学生团队、一个学期的周期内，把"校园兴趣社区"做成一个可运行、可演示的系统，是否可行。**

研究对象限定为《前景与范围报告》第 3.1 节列出的首期范围。以下内容不在本次可行性研究范围内，因为它们在范围界定阶段就已被排除：爬取学校官网与教务系统、官方业务系统的替代、跨校联动、完整的活动报名流程。

---

## 二、技术可行性

### 2.1 技术需求分析

系统需要具备的能力：

| 能力 | 技术难度 | 说明 |
| --- | --- | --- |
| 用户注册登录与权限区分 | 低 | 标准的会话与角色判断 |
| 板块、帖子、评论的增删改查 | 低 | 典型的关系型数据操作 |
| 举报与审核的状态流转 | 低 | 状态字段与权限判断，无算法难点 |
| 板块内搜索 | 低 | 数据量小，字符串匹配即可满足；后续可升级全文检索 |
| 失物招领的发布与认领 | 低 | 与帖子类似，多一个归属确认字段 |
| 组织认证与板块认领 | 低 | 审核流程，无技术难点 |
| 响应式界面 | 低 | CSS 层面即可完成 |

系统**不涉及**以下高难度技术：分布式、高并发、实时通信、推荐算法、机器学习、音视频处理、移动端原生开发。这意味着技术侧不存在"做不出来"的风险。

### 2.2 技术方案

采用全栈 JavaScript 路线：Next.js（App Router）承担服务端路由、接口与页面渲染，React 承担界面，Node 运行时提供文件型数据存储。

选择理由：

1. **前后端同语言**，团队成员只需掌握一套语言与一套工具链，减少沟通与调试成本。
2. **单体部署**，不需要额外配置数据库服务、缓存服务或容器编排，演示现场一条命令启动。
3. **文件型存储**避免原生模块编译问题，安装依赖后即可运行，不依赖外部服务可用性。
4. 存储层被封装为独立的 `store` 模块，接口按关系型数据库的语义设计，后续替换为 MySQL 或 PostgreSQL 时业务代码不需要改写。

### 2.3 技术风险

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 团队成员对 Node 生态不熟悉 | 中 | 技术选型刻意选择零配置方案；数据模型与接口在详细设计中给出字段级定义，降低实现歧义 |
| 文件型存储在并发写入下可能丢失数据 | 低（演示场景） | 采用"读取—修改—整体写回"并串行化写入；在详细设计中明确标注这是演示级简化 |
| 依赖版本升级导致构建失败 | 低 | 锁定依赖版本，构建产物随交付物一并提交 |

**技术可行性结论：可行。** 系统涉及的全部技术均为成熟方案的常规使用，没有需要预研的不确定项。

## 三、经济可行性

### 3.1 成本分析

| 成本项 | 金额 | 说明 |
| --- | --- | --- |
| 开发人力 | 0 元 | 由团队成员承担，不产生现金支出 |
| 开发环境 | 0 元 | 使用成员自有电脑与免费工具链 |
| 依赖与框架 | 0 元 | Next.js、React 均为开源免费 |
| 服务器与域名 | 0 元 | 演示在本地运行，不部署公网 |
| 短信 / 邮件验证 | 0 元 | 采用模拟校园身份验证，不接第三方服务 |

**总现金成本：0 元。**

### 3.2 收益分析

本项目是课程设计，收益体现为课程成绩与团队工程能力训练，不产生直接的商业收益。因此不做投资回报分析。

### 3.3 若后续真实运营的成本提示

如果把本设计推向真实运营，成本结构会发生根本变化，这是必须写明的部分：

- 服务器与带宽（社区类应用的内容与图片存储需求）；
- 内容审核的人力成本（UGC 平台无法用零成本维持合规）；
- 域名与备案（在中国大陆提供互联网信息服务需要 ICP 备案）；
- 若接入真实校园身份核验，需要与校方建立数据使用协议。

**经济可行性结论：课程范围内可行，现金成本为零。真实运营不具备零成本可行性，这一点在设计说明中必须如实标注。**

## 四、法律与合规可行性

这一节是本报告的核心，因为校园社区类产品的法律风险集中在这里。

### 4.1 个人信息保护

《中华人民共和国个人信息保护法》要求处理个人信息具有合法性基础并遵循最小必要原则。

- **红线**：不采集学号对应的真实身份数据用于对外展示；不接入教务、校园卡等官方业务系统的数据。
- **本设计的处理**：校园身份仅作为"平台内部的可信度标记"，不对外展示学号；注册所需的姓名与学号仅用于演示环境的模拟校验，不来自任何官方系统。
- **结论**：在"不接入官方系统、不展示学号"的前提下不构成个人信息合规风险。

### 4.2 网络信息内容生态治理

UGC 平台对用户发布的内容负有管理义务，需要具备举报、审核、处置能力。

- **本设计的处理**：举报—审核—处置闭环被列入首期范围（而非后续功能）；板块配置支持"发帖需审核"；版主与管理员具备删除内容、封禁成员的权限；处置结果可追溯。
- **缺口**：本设计**不包含**自动化内容识别能力，真实运营需要更完整的审核机制。这一点在测试报告的"未覆盖范围"中声明。

### 4.3 网站运营资质

在中国大陆境内向公众提供互联网信息服务需要 ICP 备案；涉及论坛、社区等交互式服务，备案审核要求更高。

- **本设计的处理**：系统仅作为课程演示在本地运行，不部署公网、不向公众开放，因此不触发备案要求。
- **结论**：课程范围内合规；若后续公网部署，备案与主体资质是必须的前置条件。

### 4.4 数据存储与安全

- 密码不以明文存储（演示环境使用加盐哈希）。
- 演示环境使用本地文件存储，不涉及数据出境。
- **已知简化**：演示环境使用明文 Cookie 承载会话标识，未做签名与过期控制。这是课程演示的简化，必须在详细设计中标注为待加固项。

**法律与合规可行性结论：在"不接入官方系统、不部署公网、具备举报审核闭环"的前提下可行。任何一条被打破都需要重新评估。**

## 五、操作可行性

### 5.1 用户侧

- 形态为响应式 Web，浏览器直接访问，无需安装，无版本更新成本。
- 浏览与搜索不需要登录，用户可以先看内容再决定是否注册，使用门槛低。
- 发帖需加入板块，规则单一，不需要用户理解复杂的权限体系。

### 5.2 运营侧

这是本设计刻意回避中心化运营的地方。传统校园社区需要一支团队持续拉人、发内容、做活动，学生团队做不到。本设计把运营责任下沉：

- 板块由创建者自己管理，平台不负责每个板块的活跃度。
- 治理由版主完成，管理员只在举报无法闭环时介入。
- 平台自身的职责收缩为"提供能力 + 守住底线"。

### 5.3 冷启动

冷启动是操作层面唯一无法用设计解决的问题，只能靠范围收缩：首批用户锁定为一个项目组成员自己所在的具体兴趣小组，由成员充任种子用户。面向全校铺开的冷启动在本项目条件下不可行。

**操作可行性结论：受限可行。前提是接受"单板块冷启动、运营责任下沉"的方式。**

---

## 六、组织可行性（本项目的决定性因素）

### 6.1 问题的性质

本产品的差异化主张是"组织入驻"。组织入驻型社区的核心指标是组织覆盖率，而覆盖率取决于**有人能代表一个组织做出承诺**。与其他类型的风险不同，这一条既不是技术问题，也不是资金问题，而是外部意愿问题。

### 6.2 三种方案的可行性对比

| 方案 | 需要的外部条件 | 学生团队能否独立达成 | 结论 |
| --- | --- | --- | --- |
| 组织入驻为唯一入口 | 注册社团愿意把阵地迁移过来 | 不能 | 不可行 |
| 组织入驻 + 学生自建板块（双通道） | 学生自己愿意发帖 | 能 | 可行 |
| 完全不做组织认证，只做普通论坛 | 无 | 能 | 可行，但失去差异化 |

### 6.3 本设计的选择与理由

本设计选择**双通道**：学生可自由创建板块，组织通过认证后认领或开设官方板块。理由是它把冷启动的启动条件从"说服组织"降回"有人愿意发帖"——后者是项目组自己就能满足的，而前者需要外部配合，且没有任何保证。

同时必须如实写明：**双通道方案下，组织认证的落地程度取决于外部配合，本项目无法承诺，只能承诺设计完备、流程可演示。**

### 6.4 若要做实现阶段验证

建议在需求分析定稿前，向至少一个真实的兴趣小组或注册社团做一次非正式的意向确认，并在本报告中记录结论。若无法取得任何意向，则本报告的结论应改写为"产品定位成立，组织落地未经验证"。主动如实标注依赖，比伪装成已验证更经得起追问。

**组织可行性结论：在双通道方案下可行；在唯一入口方案下不可行。**

| 阶段 | 主要产出 | 依赖关系 |

| 问题定义与选题 | 决策记录、选题定案 | 已完成 |

阶段之间存在严格的前后依赖，但**文档之间的接口是上一阶段的结论，不是上一阶段的完整内容**，因此存在并行空间：竞品分析与前景与范围可同时进行。

### 7.2 进度风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 需求蔓延 | 五个模块每个都想做深，导致文档迟迟不收敛 | 以"本期不做"清单为硬边界；实现范围以核心闭环为硬边界 |
| 文档与实现脱节 | 文档写的内容与演示工程对不上 | 文档中的接口与数据字段以演示工程的实际实现为准，出现偏差时改文档 |

**进度可行性结论：可行。** 学期周期充裕，工作分解的依赖关系清晰，主要风险是需求蔓延而非时间不足。

## 八、综合结论

**结论：项目在收敛后的范围内可行，但可行性的成立是有条件的，条件如下。**

1. **必须保持范围收缩**。五个模块为设计上限，实现只做核心闭环。任何"顺便把通知爬下来""顺便做跨校"的想法都会让可行性重新变成立论待证。
2. **必须采用双通道准入**。组织入驻是差异化层而非唯一门槛，否则冷启动不可行。
3. **必须不接入学校官方系统**。法律可行性的成立完全依赖这一条。
4. **必须把治理闭环放进首期**。UGC 平台的举报与审核不是可延后功能。
5. **必须如实标注未验证的外部依赖**。组织侧的合作意向在本报告定稿时尚未取得书面确认，这一点应当明确写出，而不是回避。

在上述条件下，本项目的技术可行性、经济可行性、进度可行性均成立，操作可行性与组织可行性受限但可控。项目可以进入需求分析阶段。

> 待核实：本校是否已有官方或第三方主导的学生社区平台（与竞品分析 O2 同一事项）；课程是否指定技术栈（O3）。两项结论若发生变化，需回写本报告第 2 节或第 6 节。
