## 一、软件产品简介

本小组拟开发的软件是 **SchoolLifeComplex，一个面向本校在校生的校园兴趣社区**，形态为响应式 Web 应用，浏览器在手机与桌面上均可使用。

它要解决的问题是：校园里的兴趣小组与注册社团目前靠微信群、QQ 群运转，内容聊过即沉，新成员看不到历史，组织者的通知重复发、难以触达；学生想找同好、想了解社团、想找丢失的物品，只能分散在多个群、多个平台、多个小程序里各处翻找。

产品提供五个功能模块：

| 编号 | 模块 | 解决的问题 |
| --- | --- | --- |
| M1 | 身份与准入 | 谁在发言、内容由谁负责、权限如何划分 |
| M2 | 兴趣板块 | 兴趣内容的组织与发现，让内容可被搜索和回溯 |
| M3 | 内容交流 | 发帖、回帖、互动，以及举报与审核的闭环 |
| M4 | 组织与活动 | 正式社团与自发小组获得自己的阵地，招新与活动有固定发布处 |
| M5 | 信息互助 | 失物招领与认领、校内公告与通知订阅 |

产品的差异化主张是**组织入驻**：任何有管理者的群体都可以开设板块，正式注册社团额外获得认证标识与官方阵地。与"再做一个校园论坛"不同，本产品把"组织是否有阵地"作为核心指标。

## 二、目标用户及市场背景

### 2.1 目标用户

| 用户角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 兴趣小组成员 | 因游戏、动漫、运动、学习等兴趣聚集的学生，规模从十几人到上百人 | 找到同好、看到历史内容、不被群消息淹没 |
| 板块创建者 / 版主 | 兴趣小组的组织者，通常是自己建群的人 | 有可管理的阵地、能沉淀内容、能约束秩序 |
| 注册社团负责人 | 校团委备案社团的负责人 | 招新有固定入口、活动通知能触达非群成员、对外有正式形象 |
| 普通浏览者 | 对本校社团和兴趣活动有兴趣、但尚未加入任何组织的学生 | 在一个地方看到有什么可参与 |
| 失物招领的发布者与失主 | 在校任何学生 | 快速发布与检索、能确认认领归属 |

### 2.2 产品定位

> 校园里的兴趣内容与组织阵地的集中地。

定位的边界需要说清楚：本产品**不是**教务、选课、成绩、校园卡等官方业务的入口，也**不试图**取代学校官方系统；它承接的是官方系统不管、而学生日常又确实需要的那部分信息与连接。

### 2.3 市场背景

需要在本节说明的市场事实：

1. 校园内的兴趣社群天然存在且活跃，但承载工具是即时通讯群组，特点是"高流量、低沉淀"。
2. 校内官方渠道（教务系统、学院通知、公众号）负责权威信息，但不承载学生之间的兴趣连接。
3. 面向高校的第三方综合平台已经存在多年，多以官方数据接入（课表、成绩、校园卡）为核心竞争力，兴趣社区通常是附属功能。

> 待核实：本校是否已有官方或第三方主导的学生社区类平台、其上线时间与覆盖范围。这一事实直接决定第 2.3 节的结论强度，需在定稿前向学生会或信息化办公室确认。

## 三、竞品分析

按课程要求，本次选取三类各一款竞品，通过文档查询与实际下载使用两种途径获取信息。

### 3.1 校内综合平台：今日校园

**产品概况**：面向高校的综合服务类应用，以学校官方数据接入为基础，提供课表、成绩、校园卡、通知、请假等服务，多数高校以学校为单位进行部署。

**与本产品重叠的功能**：校内通知的集中查看（对应 M5 的公告部分）、少量校园社交与活动信息（对应 M4 的边缘）。

**优点**

- 与学校官方系统打通，通知具有权威性与强制性触达能力，这是任何学生自建产品都无法复制的优势。
- 覆盖学业与生活事务，使用频率由官方业务驱动，不需要靠内容运营维持活跃。

**缺点**

- 内容由学校单向发布，学生之间无法形成讨论。
- 兴趣类内容不是它的目标，游戏、动漫这类板块在其中没有生长空间的定位。
- 各校独立部署，体验与功能以学校采购为准，学生的诉求难以影响产品。

**可参考内容**

- 通知的呈现方式：按来源与时间归类、重要通知的强调方式。
- 身份体系：与学号绑定的账号与权限划分方式。

> 待核实：实际下载使用记录（版本号、使用日期、截图）。

### 3.2 校园社区：QQ 频道

**产品概况**：QQ 内置的兴趣社区能力，以"频道—子频道—帖子/房间"的方式组织，在校园与游戏社群中有相当规模的用户基础。

**与本产品重叠的功能**：兴趣板块的组织（M2）、内容发布与互动（M3）、组织阵地（M4）。

**优点**

- 依附于 QQ，用户无需新增注册成本，触达与拉新几乎为零阻力。
- 板块与子频道结构与本产品设想的板块模型高度接近。
- 内容有留存形态，比纯聊天群更适合沉淀。

**缺点**

- 组织者身份没有认证机制，"官方社团阵地"与"任何人开的频道"在形态上无法区分。
- 与 QQ 账号体系绑定，与校园身份的关联需要用户自己声明，失物招领这类需要可信身份的场景缺少约束力。
- 非 QQ 用户（例如主要使用微信的学生）被排除在外。
- 校园场景下的审核与举报能力由平台统一提供，板块自治者缺少本地化治理工具。

**可参考内容**

- 板块分级结构（频道—子频道—话题）的信息架构。
- 内容卡片的呈现方式与信息密度。

> 待核实：实际下载使用记录（版本号、使用日期、截图）。

### 3.3 垂类兴趣社区：TapTap 社区

**产品概况**：以游戏玩家为核心的社区与分发平台，社区按游戏划分板块，玩家在板块内发帖、评分、讨论攻略。

**与本产品重叠的功能**：兴趣板块的组织（M2）、内容交流（M3）、内容沉淀与检索。

**优点**

- 按兴趣对象划分板块的逻辑非常清晰，一个游戏一个社区，用户第一眼就知道自己该去哪个板块。
- 内容沉淀与检索做得好，攻略、测评能长期被后来的玩家翻到，社区价值随时间累积。
- 有明确的内容质量分层（精华、攻略、讨论），引导优质内容。

**缺点**

- 面向全国玩家，与"本校"这一地理与身份边界无关，无法承载社团招新、失物招领这类校园场景。
- 组织者是平台与官方运营，不是学生组织，"组织入驻"的概念不成立。
- 内容以游戏为限，动漫、运动、学习类兴趣无处安放。

**可参考内容**

- 板块划分与发现路径的设计。
- 内容质量分层与精华机制。
- 举报与治理的用户可见性（举报后用户能看到什么）。

> 待核实：实际下载使用记录（版本号、使用日期、截图）。

### 3.4 现状替代方案

这三类竞品之外，学生实际使用的方案还包括微信群、QQ 群与社团自己运营的公众号。它们不计入三款竞品，但必须写进背景，因为它们是真正的替代品：

- **微信群 / QQ 群**：触达快、零成本，但内容无沉淀、新人看不到历史、搜索几乎不可用、无法按主题分类。
- **社团公众号**：有正式形象，但单向发布、无讨论、依赖人工推送，且开通与排版成本对小型社团偏高。

### 3.5 对比汇总

| 维度 | 今日校园 | QQ 频道 | TapTap 社区 | 微信群/QQ群 | 本产品 |
| --- | --- | --- | --- | --- | --- |
| 校园身份关联 | 强（学号绑定） | 无 | 无 | 无 | 中（可认证） |
| 内容可沉淀可搜索 | 不适用 | 中 | 强 | 无 | 强 |
| 组织认证 | 官方组织 | 无 | 平台运营 | 无 | 有（认证标识） |
| 板块自治 | 无 | 弱 | 弱 | 无 | 强（版主机制） |
| 校园场景适配 | 强（官方业务） | 中 | 无 | 强 | 强 |
| 冷启动成本 | 低（官方驱动） | 低（QQ 导流） | 低（游戏导流） | 最低 | 高 |

### 3.6 分析结论

1. **"统一入口"不是本产品的卖点**。官方业务入口已经被今日校园一类产品占据，且其优势来自学校采购与数据授权，学生团队无法竞争。本产品必须放弃"集齐校园功能"的叙事。
2. **"内容沉淀"是真实且未被满足的需求**。微信群与 QQ 群的问题不是功能少，而是内容留不住；QQ 频道解决了形态问题，但没有解决组织身份问题。
3. **"组织认证"是本产品唯一没有被现有产品覆盖的位置**。校内社区里，"谁代表一个正式组织发言"这件事目前无人负责，而这恰好是社团最在意的东西。
4. **最大风险不是竞品而是冷启动**。三款竞品都不需要从零获取用户：今日校园靠学校统一部署，QQ 频道靠 QQ 导流，TapTap 靠游戏分发。本产品没有任何现成流量入口，因此首批场景必须收缩到一个具体的小组，而不是面向全校铺开。

## 四、软件功能规划

基于上述分析，功能规划遵循三条原则：以内容沉淀为主价值、以组织认证为差异化、以板块自治替代中心化运营。

### 4.1 功能范围与优先级

| 模块 | 功能项 | 优先级 | 依据 |
| --- | --- | --- | --- |
| M1 身份与准入 | 注册与登录 | 高 | 一切权限判断的前提 |
| M1 | 校园身份认证状态 | 中 | 失物招领等场景需要可信身份，但不应阻断浏览 |
| M1 | 个人主页 | 中 | 内容与作者关联，形成责任感 |
| M1 | 权限与信誉 | 中 | 版主自治与封禁的依据 |
| M2 兴趣板块 | 板块创建（自建通道） | 高 | 双通道准入的入口之一 |
| M2 | 板块分类与发现 | 高 | 解决"新人不知道该去哪"的问题（参考 TapTap） |
| M2 | 加入板块 | 高 | 发帖权限的前置条件 |
| M2 | 板块内自治（版主） | 高 | 替代中心化运营，也是差异化的载体 |
| M3 内容交流 | 发帖（支持需审核配置） | 高 | 核心内容生产 |
| M3 | 回帖与互动 | 高 | 讨论形成的前提 |
| M3 | 举报 | 高 | 治理闭环的入口 |
| M3 | 版主审核与处置 | 高 | 治理闭环的出口，UGC 场景的必备能力 |
| M4 组织与活动 | 组织认证入驻 | 中 | 差异化主张的落地 |
| M4 | 认领板块为官方阵地 | 中 | 把"组织"与"板块"绑定 |
| M4 | 组织主页与招新信息 | 低 | 季节性需求，先以板块内信息形态存在 |
| M5 信息互助 | 失物招领发布与认领 | 中 | 校园刚需，且验证身份机制的价值 |
| M5 | 公告与通知订阅 | 低 | 通知聚合的降级形态 |

### 4.2 本期不做

以下内容明确排除在本期设计与实现之外，理由在可行性研究报告中展开：

- 爬取学校官网、教务系统或任何官方业务系统。
- 成绩、课表、校园卡等官方业务功能的替代。
- 跨校（大学城多校）联动。
- 完整的活动报名与签到流程。

### 4.3 实现策略

设计与文档覆盖五个模块，演示环节只实现核心闭环：**注册登录（模拟校园身份）→ 创建板块 → 加入板块 → 发帖 → 评论 → 举报 → 版主处置**，另附失物招领的发布与认领。其余功能在详细设计中给出接口与流程定义，标注为待实现。
