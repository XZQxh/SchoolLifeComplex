## 二、测试策略

### 2.1 测试层次

| 层次 | 手段 | 覆盖目标 |
| --- | --- | --- |
| 接口级端到端 | `demo/smoke-test.js`，以真实 HTTP 请求驱动完整业务链路 | 权限判定、状态流转、治理闭环、失物招领 |
| 界面渲染 | `demo/scripts/ui-check.mjs`，无头浏览器加载页面并读取渲染结果 | 页面可用性、客户端渲染是否正确、移动端布局 |

### 2.2 为什么采用接口级端到端而不是单元测试

本项目的风险集中在**权限判定与状态流转**上，而不是单个函数的算法正确性。单元测试无法暴露"某个接口忘了校验成员关系"这类缺陷，因此测试重心放在以真实身份组合（游客、普通成员、版主、管理员）依次发起请求，观察系统是否拒绝越权操作并保持状态一致。

### 2.3 测试数据

测试使用独立的测试账号（学号前缀 `T`）与独立板块，不污染种子数据中面向演示的内容。每次执行前重置数据文件。

## 五、缺陷记录

### DEF-01 移动端顶部导航只剩图标，含义不可辨

- **发现方式**：人工核对移动端截图。
- **现象**：窄屏下导航链接的文字被隐藏，只保留图标。三个图标分别代表组织入驻、失物招领与治理台，缺少文字后无法判断去向，移动端也没有悬浮提示。
- **严重程度**：中。
- **处理**：修改为窄屏下折行布局，导航独占一行并保留文字标签。复测通过（UI-02 截图确认）。

### DEF-02 测试脚本的输出在管道中被截断

- **发现方式**：执行 `node scripts/ui-check.mjs` 时进程退出码为 0，但终端没有任何输出，测试结果无法查看。
- **原因**：脚本在结尾调用 `process.exit()`。当标准输出被重定向到管道时，写入是异步的，进程提前退出会丢弃尚未刷出的缓冲内容。
- **严重程度**：中（影响测试结论的可验证性）。
- **处理**：改用 `process.exitCode` 并让进程自然退出。复测后 6 项界面用例的输出完整可见。

### DEF-03 举报用例的目标选择错误，掩盖了真实流程

- **发现方式**：首轮执行时 TC-15 失败。
- **原因**：用例让用户乙举报**自己发布**的帖子，系统按设计返回 400 `VALIDATION`，用例预期与系统行为不一致。这不是产品缺陷，而是测试用例设计错误；但它同时说明一个真实风险：如果用例设计不当，会掩盖"举报—处置"链路并未被真正执行。
- **严重程度**：高（用例缺陷）。
- **处理**：改为举报他人内容，并补充"重复举报合并""驳回后离开队列""版主可举报他人内容"三条用例，使治理链路被完整走通。

### DEF-04 点赞权限在文档与实现之间不一致

- **发现方式**：编写测试用例时对照需求分析报告的权限矩阵与总体设计报告的接口清单。
- **现象**：权限矩阵要求"发帖 / 评论 / 点赞"均由板块成员执行，而接口清单把点赞标注为"登录"即可。
- **严重程度**：低（文档一致性）。
- **处理**：以实现为准（点赞需要板块成员身份），修正总体设计报告的接口清单，并在详细设计报告中补充该接口的 `FORBIDDEN` 错误码。

## 七、测试结论

1. **核心闭环成立**：注册登录 → 创建板块 → 加入板块 → 发帖 → 评论 → 举报 → 版主处置，七个环节全部走通，与《总体设计报告》的接口清单一致。
2. **权限模型有效**：游客、注册用户、板块成员、版主、管理员五类身份的行为差异符合需求分析报告的权限矩阵；越权操作均被服务端拒绝，且未观察到副作用。
3. **治理闭环有效**：举报可提交、可合并、可驳回、可结案；封禁动作对后续行为确实生效。
4. **审核状态机有效**：板块级审核开关生效，待审内容的可见范围（作者与版主可见、游客不可见）符合设计。
5. **界面可用**：桌面端与移动端均可正常使用，无横向溢出与元素重叠。
6. **残余风险集中在演示级简化**：全部 9 项未覆盖内容都来自详细设计报告已声明的简化项，或需求分析报告中明确标注为"仅设计"的需求，没有出现"设计与实现不符"的隐性缺陷。

**测试意见：可以提交演示。** 演示前应执行 `npm run reset` 将数据恢复为种子状态，并按《演示说明》走一遍核心闭环。
