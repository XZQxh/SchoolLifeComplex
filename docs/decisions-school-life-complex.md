# 决策记录：SchoolLifeComplex 选题与内容方向

本文件记录选题定型过程中每一条结论及其理由，另列待定问题。新增结论直接追加，不覆盖历史条目；被推翻的结论保留原文并标注状态。

---

## 一、已确定的结论

### D1 项目主题

**结论**：项目定为"面向本校在校生的校园兴趣社区"，载体为响应式 Web。

**理由**：原设想是"学校生活功能的统一集合体"，包含兴趣交流、学校通知集成、失物招领与学生会申请、大学城联动四块。经过讨论，这四块实际分属三种产品形态——聚合器、社区、事务工具——它们的价值来源和失败条件互不相关（聚合成败看授权、社区成败看用户密度、工具成败看流程对接），拼在一起不会互相增强，只会让范围乘以三。课程要求"3~5 个问题（功能模块）"，原方案摊开后至少六个功能域，超出"规模适中"的口径。因此收敛为单一形态。

### D2 差异化主张

**结论**：差异化主张为**组织入驻型社区**。

**理由**：项目组成员的选择。"统一入口"是实现方式而非用户价值，答辩时无法回答"学生为什么不用今日校园、QQ 频道、表白墙"这一问。组织入驻提供了可陈述的价值：让校园里的正式社团与自发兴趣小组都拥有可沉淀内容的阵地，正式组织获得认证标识。

**已知代价**：组织入驻型社区的核心指标是组织覆盖率，必须有人代表组织做出承诺，这会把项目的关键外部依赖从技术挪到组织，直接影响可行性研究报告的"组织可行性"一节。

### D3 "组织"的定义

**结论**：组织 = 任何有管理者的群体。学生自建的兴趣小组与注册社团同属"组织"，后者额外获得认证标识。

**理由**：若只承认注册社团与学生会，则首批需求场景（一个具体游戏小组）与主张自相矛盾——游戏小组通常没有公章、没有指导老师，没有人能"代表组织"入驻。扩展定义后，首批场景仍然是团队自己熟悉的游戏小组，需求不必凭空编造，同时正式社团的认证层作为差异化保留在设计里。

### D4 双通道准入

**结论**：学生可自由创建板块；组织通过认证后认领或开设官方板块。组织入驻是差异化层，不是唯一入口。

**理由**：如果板块只能由组织开设，冷启动就变成"说服组织"，而这是三个人在一学期内做不到的事。双通道把冷启动降回"有人愿意发帖"的量级，团队自己就能完成。同时"认证组织"这一层仍是差异化，不会被削弱。

### D5 服务边界与首批场景

**结论**：服务边界为本校全校（远期）；首批需求场景锚定**一个具体游戏小组**。

**理由**：社区产品不是"全校一起冷启动"，而是按板块逐个冷启动——一个板块至少需要几十个有互动意愿的人才有内容可看。因此"全校"只能是远期服务边界，需求分析必须指定一个可采访、可观察的第一批用户群，否则需求变成凭空想象，答辩时经不起"你怎么知道学生需要这个"的追问。团队自己就在游戏小组里，是最低成本的取材来源。

### D6 板块可见性与准入

**结论**：所有人可浏览与搜索，加入后才能发帖，发帖可配置为需审核。

**理由**：搜索可见是社区价值成立的前提——如果内容不可搜，社区与私密群聊没有区别，内容沉淀的主张也就不成立。发帖需加入是为了形成最低限度的成员归属，同时为版主自治提供权限边界。可配置审核让敏感板块（如校内话题）能收紧，而娱乐板块保持流畅。

### D7 五个功能模块

**结论**：M1 身份与准入、M2 兴趣板块、M3 内容交流、M4 组织与活动、M5 信息互助。

**理由**：取课程"3~5 个问题"区间的上限。取上限的原因不是工作量小，而是文档最怕"没有素材可写"：五个问题域能让需求分析与总体设计各自有实质章节，身份与治理独立成模块后，认证状态、板块归属、帖子与举报、审核处置都是现成的状态机，状态转换图和用例图有内容可画。

### D8 通知聚合与跨校联动的处置

**结论**：通知聚合降级为社区内的公告板块（官方订阅 + 人工发布，不爬取教务与官网）；跨校联动只作为前景与范围报告中的未来展望。

**理由**：爬取学校官网与教务系统涉及个人信息保护合规与校方授权，是可行性报告里最容易被追问的一环；大学城联动需要多校的组织协作，单校课程项目无法验证。降级不等于删除，两者仍以"公告板块"和"未来展望"的形式保留在文档中，但不占用本期设计与实现的工作量。

### D9 技术路线

**结论**：响应式 Web，全栈 JS（Next.js）。演示工程使用 Next.js App Router + Node 运行时 + 文件型数据存储。

**理由**：三人到四人小组在一个学期内，"能跑起来"比"架构好看"重要。前后端同语言、单体部署，演示现场一条命令即可启动。文件型存储避免了原生模块编译与外部数据库服务，演示环境零配置；存储层被封装为独立模块，后续替换为关系数据库时不影响业务代码。

### D10 交付物与实现范围

**结论**：课程文档按七类全覆盖规划；实现侧收敛为一条可跑的核心闭环。

**理由**：课程明确"主题可以不实现，但实现并展示可加分"，而文档是计分主体。因此设计与文档覆盖五个模块，实现只做核心闭环：注册登录（模拟校园身份）→ 创建板块 → 加入板块 → 发帖 → 评论 → 举报 → 版主处置。另按验收要求补上失物招领的发布与认领。

### D11 竞品取样

**结论**：三类各取一款——校内综合平台（今日校园）、校园社区（QQ 频道）、垂类兴趣社区（TapTap 社区）。微信群/QQ 群与社团公众号作为"现状替代方案"写进背景，不计入三款竞品。

**理由**：竞品分析模板要求至少三款，且必须走"文档查询 + 下载详细使用"两条途径。三类跨度的对比才能证明"整合校园服务"这个位置的真实处境：校内综合平台占据官方数据入口，校园社区占据用户密度，垂类社区占据内容深度。只在校园社区类内部比较，会被追问"为什么不做垂类对比"。

### D12 团队与分工

**结论**：团队 4 人，项目经理负责协调、成员表与总结汇报，并兼任至少一个文档角色。七份文档的具体分配由组内商定，不在本记录范围内。

**理由**：课程要求团队一般不超过 4 人、每人至少完成一份文档、项目经理也必须担任具体角色。具体分配属于组内管理事务，与本选题的内容方向无关，故不在此固化。
