# 前景与范围报告

> 项目：SchoolLifeComplex 校园兴趣社区
> 编写：系统分析员1
> 版本：初稿
> 依据：本报告的前景描述与范围边界以《决策记录》D1–D11 为准。

---

## 一、业务需求

### 1.1 背景

校园里的兴趣社群数量多、活跃度高，但承载工具长期是即时通讯群组。群组解决了"即时触达"，没有解决"内容留存"：一次讨论结束，内容就沉到聊天记录底部；新加入的成员无法知道群里曾经讨论过什么；组织者的通知需要反复重发，稍有间隔就有人没看到。

与此并行的是组织一侧的需求。注册社团每年招新时需要在多个群、多个平台重复投放信息，活动通知难以触达非群成员；而自发形成的兴趣小组虽然活跃，却没有办法对外表明"我们是一个稳定的群体"。

学校官方系统承担的是权威信息的发布与业务流程的办理，它不负责学生之间的兴趣连接。这块空白目前由大量重复、分散、不可检索的群聊填补。

### 1.2 业务机会

> 把校园里"已经存在但留不住"的兴趣内容，收拢到一个可搜索、可回溯、有组织归属的地方。

这个机会的成立条件有三条，缺一不可：

1. 内容能被未加入的人搜到，否则与私密群聊没有区别。
2. 组织者愿意把阵地放过来，因此组织需要一个可确认的身份。
3. 内容量不必一开始就大，但必须在一个板块内形成"能找到有用信息"的密度。

### 1.3 业务目标与成功标准

| 目标 | 成功标准（首期，以一个兴趣小组为观察对象） |
| --- | --- |
| 内容可沉淀 | 小组的历史讨论在一个板块内可分类、可搜索，新成员能独立找到既往的入门信息 |
| 组织有阵地 | 至少一个注册社团或正式小组在其板块上显示认证标识 |
| 治理可闭环 | 举报内容能进入待审状态并被版主处置，处置结果对举报者可见 |
| 秩序可控 | 未加入板块的用户只能读、不能发，越权行为被权限模型拒绝 |

> 说明：本项目的成功标准以"闭环是否成立"为准，不以用户量或活跃度为准。学生团队的课程项目无法承担运营指标，把它写成日活目标只会让文档失真。这正是竞品分析结论 4 所指出的：本产品最大的风险不是竞品，而是冷启动。

### 1.4 业务风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 冷启动失败 | 板块没有内容，用户来一次就走 | 首批场景收缩到一个具体小组，由项目组成员自己充任种子用户 |
| 组织不配合 | 没有组织愿意入驻，差异化主张落空 | 采用双通道准入：自建板块先行，组织认证作为加成而非门槛 |
| 内容治理失控 | 出现攻击、诈骗、违规内容 | 举报—审核—处置闭环进入首期范围，不作为后续功能 |
| 与官方平台冲突 | 学校已有同类平台，产品重复 | 明确不做官方业务替代，只做官方不管的学生侧连接 |
| 身份可信度不足 | 无学号认证时，失物招领等场景易被冒领 | 以信誉与举报约束替代强制实名，在需求分析中明确约束条件 |

## 二、前景说明

### 2.1 产品前景

> 对在校学生：一个能按兴趣找到同好、能查到别人已经讨论过的内容、能在一个地方看到学校社团在做什么的网站。
>
> 对兴趣小组与社团组织者：一个可以自己管理、内容不会消失、能对外展示正式身份的阵地。

产品的形态是响应式 Web 应用，在手机与桌面浏览器上均可使用，无需安装。

### 2.2 主要特性

| 编号 | 特性 | 面向的用户价值 |
| --- | --- | --- |
| F1 | 按兴趣组织的板块，可浏览、可搜索、可分类发现 | 新人知道自己该去哪 |
| F2 | 加入后发帖、回帖、互动 | 参与门槛清晰，讨论可累积 |
| F3 | 版主自治：板块由创建者或指定成员管理 | 治理贴近内容，不依赖中心化运营 |
| F4 | 举报与审核处置闭环 | 出现问题时有人管、有记录 |
| F5 | 组织认证与官方板块 | 正式组织有可识别的身份 |
| F6 | 失物招领发布与认领 | 校园高频刚需，验证身份机制的价值 |
| F7 | 公告与通知订阅 | 组织信息有固定发布处，替代重复群发 |

### 2.3 假设与依赖

**假设**

- 学生愿意为"内容能留存"付出一次注册成本。若这个假设不成立，产品价值不成立。
- 兴趣小组的组织者有管理板块的意愿。
- 校方对学生自建社区不持禁止态度（见可行性研究报告的组织可行性与法律可行性）。

**依赖**

- 组织认证环节若要与真实社团备案信息核对，需要校团委或社团联合会的配合。首期以"人工核验 + 声明"降级处理，不阻塞设计。
- 演示环境依赖浏览器，无需安装客户端。

## 三、范围与限制

### 3.1 首期范围（本期设计与实现）

| 范围项 | 内容 |
| --- | --- |
| 身份与准入 | 注册登录、模拟校园身份认证状态、角色与权限（学生 / 版主 / 管理员） |
| 兴趣板块 | 创建板块、分类浏览、搜索、加入板块、板块自治权限 |
| 内容交流 | 发帖（可配置需审核）、评论、互动、举报 |
| 治理 | 举报列表、版主与管理员处置、处置结果反馈 |
| 组织与活动 | 组织注册与认证、认领板块为官方阵地、认证标识展示 |
| 信息互助 | 失物招领发布、检索、认领状态流转 |
| 公告 | 板块内公告的发布与浏览（人工发布形态） |

### 3.2 明确排除（本期不做）

- 爬取学校官网、教务系统或任何官方业务系统。
- 成绩、课表、校园卡、选课等官方业务的替代或集成。
- 跨校（大学城多校）联动。
- 完整的活动报名、签到与积分流程。
- 即时通信（私聊、群聊）。
- 移动端原生应用与小程序。

### 3.3 后续范围（本期之外，仅作方向说明）

按推进成本从低到高排列，作为产品路线图，不作为本期承诺：

1. **第二个板块的冷启动**：在首个小组站稳后，按同样的方式复制到相邻的兴趣圈层。
2. **组织认证的流程化**：把人工核验升级为可提交材料、可追溯的审核流程。
3. **活动能力的补全**：招新报名、活动签到、参与记录。
4. **消息提醒**：订阅内容的更新提醒。
5. **跨校联动**：把服务边界从本校扩展到大学城其他高校。

### 3.4 关于跨校联动的说明

跨校联动是项目最初的设想之一，也是本报告唯一保留在展望中的原始模块。它被移出本期范围的理由是：跨校意味着多所学校的组织协作、跨校的身份体系与数据边界、以及多校各自的内容治理责任，这些都不是单个学生团队在一学期内能够验证的事情。

它作为方向是成立的——大学城的学生在兴趣层面本就跨校聚集，地理上的邻近会放大社区的价值。但它成立的前提是"单校模式被验证"，因此它的正确位置是路线图的最后一步，而不是首期的一个模块。

## 四、业务环境

### 4.1 相关方

| 相关方 | 与本产品的关系 | 关注点 |
| --- | --- | --- |
| 在校学生 | 主要用户 | 内容有用、使用门槛低、不被广告与垃圾信息干扰 |
| 兴趣小组组织者 | 板块创建者与版主 | 有管理权限、内容不流失、工具不难用 |
| 注册社团负责人 | 组织认证申请者 | 对外形象正式、招新触达面更广 |
| 学生会 / 社团联合会 | 潜在的组织认证核验方 | 内容合规、组织身份真实 |
| 校信息化管理部门 | 外部约束方 | 系统安全、数据合规、不使用官方数据 |
| 任课教师 | 评审方 | 需求来源真实、设计与文档自洽、边界清晰 |

### 4.2 项目优先级

当资源不足时，按以下顺序取舍：

1. 保证文档完整与自洽（课程计分主体）。
2. 保证核心闭环可运行（演示加分）。
3. 保证五个模块的设计深度一致（避免某个模块只有一句话）。
4. 补充模块 4 与模块 5 的实现（锦上添花）。
